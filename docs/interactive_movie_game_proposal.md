# 历史题材交互影游生成系统：实现方案讨论稿

**版本：** 0.2  
**日期：** 2026-10-31

## 1. 项目定位

项目面向历史事件和经典战例，目标是让用户输入一个主题，系统据此生成一份有史料依据、带分支选择、可继续制作成影游的内容包。

系统的核心产物不是直接生成完整影片，而是先生成可审阅、可迭代的剧本与制作资料：史实卡片、故事大纲、分支图、场景脚本、选择后果、旁白/对白、镜头与素材建议，以及可供播放器读取的结构化剧情文件。视频可以先用占位素材验证；后续再接入拍摄素材或媒体生成能力。

推荐采用 **Agent + Skills + Workflow**：Agent 负责理解主题和调度，Skills 封装可复用的专业能力，Workflow 固定各步骤、输入输出和质量检查。

## 2. 使用方式与默认值

用户可以只提供主题，例如“赤壁之战”“长平之战”或“郑和下西洋”。系统直接开始生成，不要求用户先填写完整需求表。缺少信息时采用默认值，并在结果的项目设定中列出，用户可以再修改。

建议默认值：

- 受众：普通历史兴趣用户。
- 体验时长：约 10–15 分钟。
- 交互密度：3–5 个关键选择。
- 叙事视角：以一个合理的观察者或参与者呈现场景，不把玩家伪装成真实历史人物。
- 史实尺度：重要时间、地点、人物关系和事件结果尽量有来源支持；戏剧化场景、合成人物和虚构对白明确标注。
- 交付形态：人类可读的方案文档 + 可校验的剧情 JSON + 史料与改编说明。

若主题范围过宽，Agent 先选取一个适合短篇表达的切面，并说明取舍；只有当主题存在实质性歧义、会导致完全不同的作品时才追问。

## 3. 系统结构

```text
用户主题
   ↓
影游生成 Agent（理解意图、设置默认值、调度步骤）
   ↓
Workflow：主题定界 → 史料整理 → 戏剧结构 → 分支剧本 → 校验与打包
   ├── 历史研究 Skill
   ├── 影游改编 Skill
   ├── 分支结构设计 Skill
   ├── 剧情格式编写 Skill
   └── 史实与结构校验 Skill
   ↓
方案文档 + 史料卡片 + 分支图 + 剧情数据 + 制作清单
```

### Agent

Agent 是面向用户的入口，负责：

- 将简短主题转成项目 brief，补齐可默认的受众、篇幅和风格。
- 判断主题类型与时间范围，选择合适的 Workflow。
- 将中间产物传给对应 Skill，并保留来源和改编记录。
- 汇总结果、说明默认假设和待确认的历史争议。
- 根据用户反馈局部重写，例如“加强守城视角”或“减少战斗描写”。

Agent 不应把所有工作塞进一个超长提示词。研究、叙事、结构化输出和校验应有独立的输入输出约定，方便单独改进和复用。

### Skills

1. **历史研究 Skill**：围绕主题整理时间线、主要人物、地点、事件因果、结果和争议点；为每条重要史实记录来源、原文定位或链接、可信程度及适用范围。
2. **历史影游改编 Skill**：把史实整理成适合影像表达的故事切面、人物目标、冲突和场景；区分“可证史实”“合理推演”和“戏剧虚构”。
3. **分支结构 Skill**：设计玩家能理解的选择、即时或延迟后果、分支汇合点与结局条件；避免只有选项文案变化、剧情却没有后果的伪分支。
4. **剧情数据 Skill**：按项目约定的 schema 输出节点、素材引用、字幕/对白、选项、状态变化、条件和后继节点。
5. **校验 Skill**：检查史实引用、节点引用、分支可达性、结局可达性、状态变量、缺失素材和格式错误，并给出可定位的问题清单。

Skill 是专业操作说明和输出规范；是否调用、调用顺序和结果衔接由 Agent/Workflow 决定。

### Workflow

Workflow 负责把可变的语言生成组织成可重复执行的步骤。每一步都应有明确产物和进入下一步的条件，不依赖模型“记得”前面做过什么。

## 4. 从主题到交付物的生成流程

### 第一步：建立项目 brief

输入主题，识别事件、时代、涉及人物和主题边界。生成 brief，包含默认受众、目标时长、交互密度、叙事视角和史实尺度。用户仅给主题时直接采用默认值。

### 第二步：整理史料包

先形成事实底稿，再写故事。史料包至少包含：

- 事件时间线与关键节点。
- 主要人物、阵营、目标和关系。
- 地理与军事背景（适用于战例）。
- 关键因果和事件结果。
- 有争议或来源不一致的说法。
- 每项重要陈述的来源记录。

来源可以来自项目维护的可信资料库或明确允许的检索工具。检索结果要保留标题、作者/机构、出版信息、链接或定位。不能把模型记忆当作史料引用；找不到依据时应降格为待核实内容或从剧本中移除。

### 第三步：确定故事切面

从史料包中选择一个可在目标时长内讲清楚的冲突，例如一次决策、一段行军/守城过程、一名使者的任务，或战役前后的关键抉择。输出故事大纲、主要角色、场景列表，以及哪些内容是史实、推演或虚构。

### 第四步：设计交互分支

先画节点图，再写完整场景。每个选择都说明：玩家当时知道什么、选择表达了什么、状态如何变化、后果何时出现、是否会改变后续场景或结局。战役结果等已确定史实不因玩家选择而被改写；玩家影响的是体验视角、局部任务、信息获取、人物关系或战后评价。

### 第五步：编写场景脚本

为每个节点生成场景目的、环境与人物、动作、旁白/对白、字幕、建议时长、选择出现时机和素材需求。对白如非史料原文，应标为“创作对白”；对真实人物的私密动机和未记录谈话避免写成确定史实。

### 第六步：校验并打包

运行史实检查和结构检查。修复阻断问题后，输出方案文档、史料包、分支图、场景脚本、剧情 JSON 和素材清单。报告仍需人工判断的争议，不将其藏在最终文案里。

## 5. 核心数据约定

每条历史事实使用稳定 ID，并让剧情节点引用事实 ID。这样可以追溯某场戏依据什么写成，也能在史料更新时定位受影响的内容。

```json
{
  "project": {
    "theme": "示例历史主题",
    "defaults": { "duration_minutes": 12, "audience": "普通历史兴趣用户" }
  },
  "facts": [
    {
      "id": "fact_001",
      "claim": "待填写的历史陈述",
      "status": "supported",
      "source_ids": ["source_001"],
      "notes": "适用范围或争议说明"
    }
  ],
  "nodes": [
    {
      "id": "scene_001",
      "type": "scene",
      "fact_refs": ["fact_001"],
      "adaptation_labels": ["historical_fact", "fictional_dialogue"],
      "media": null,
      "choices": [
        { "id": "choice_001", "label": "选项文字", "effects": {}, "next": "scene_002" }
      ]
    }
  ]
}
```

字段是讨论稿，正式 schema 应在 MVP 早期冻结版本号，并为升级保留迁移策略。建议至少包含来源表、事实状态、改编标签、条件表达式、节点和结局信息。

## 6. 质量规则

### 史实质量

- 重要时间、地点、人物、因果和结果必须能追溯到来源。
- 多来源冲突时记录冲突，不擅自伪装成定论。
- 逐字引语必须有出处；无法核实的对白标成创作对白。
- 明确区分史实、合理推演、戏剧虚构和待核实内容。
- 玩家选择不改变已确立的历史结果，除非作品明确采用架空历史设定并标识。

### 交互质量

- 每个选择应影响至少一个可观察结果：信息、局部路径、人物关系、资源/风险或结局评价。
- 所有节点可达，所有结局可由有效路径到达；不能出现悬空引用或无出口节点。
- 检查分支汇合是否合理、重复观看负担是否可接受。
- 选择文案应符合角色视角和当时已知信息。

### 输出质量

- 剧情 JSON 可解析并通过 schema 校验。
- 文档、节点图和结构化数据中的节点名称、顺序和结局一致。
- 未完成的视频素材以明确占位符呈现，不能误报为已生成成片。

## 7. MVP 建议

先实现一个主题到“可评审内容包”的端到端 Workflow，不急于做复杂 Agent 社群或完整视频播放器。

**MVP 输入：** 一个历史事件或经典战例主题。  
**MVP 输出：** brief、带来源的史料卡、故事大纲、3–5 个关键选择的分支图、场景脚本、剧情 JSON、校验报告和素材清单。  
**MVP 暂不负责：** 自动拍摄、完整视频生成、账号系统、多人协作、商业化和开放式剧本编辑器。

建议按此顺序交付：

1. 固定剧情 schema、事实/虚构标记和来源记录格式。
2. 做通单主题 Workflow，并支持本地保存每一步产物。
3. 加入自动格式和图结构校验，再补充史实引用检查。
4. 用 2–3 个不同类型的历史主题做内部试跑，检查模板是否泛化。
5. 再接入影像播放器、素材管理或媒体生成能力。

## 8. 如何判断 MVP 有效

- 只输入主题，能稳定得到完整且结构一致的内容包。
- 关键史实都有可检查的来源；争议和创作内容能被清楚识别。
- 剧情图无断路，选择后果在脚本和数据中一致。
- 编剧/历史顾问可以指出具体段落并要求局部重写，不必从头生成。
- 不同类型主题都能复用主流程，只有少量领域提示需要替换。

## 9. 待讨论的实现决策

- 史料来源先使用项目内维护的资料库，还是在 Workflow 中进行受控联网检索？
- 第一阶段的交付目标是供编剧审核的剧本包，还是直接接入一个可播放原型？
- 对史实准确度是否设置历史顾问审核环节？哪些主题需要强制审核？
- 是否提供“忠实史实 / 适度戏剧化 / 架空改编”三档创作模式？
- Skill 与 Workflow 的具体运行平台、存储格式和版本管理方式是什么？

这些问题不会阻止先做端到端内容生成原型；可以先采用项目内来源清单、剧本包交付、适度戏剧化但明确标注的默认策略，再根据试跑结果调整。

## 10. 开始实现前要准备什么

### 启动前要定下来的四项

1. **首个试跑主题：** 选一个边界清楚、资料容易核对的历史事件或战例。它将作为 Workflow 的验收样例。
2. **史料来源策略：** 明确第一版使用项目提供的资料、受控联网检索，还是两者结合；准备来源记录格式和最低引用要求。
3. **第一阶段交付物：** 建议先交付“可审核的剧本内容包”，包含史料卡、分支图、场景脚本、剧情 JSON 和校验报告；先不要求成片。
4. **运行入口：** 选本地命令行/脚本、网页界面或现有 Agent 平台。此项决定如何接模型、Skill 和 Workflow，但不影响先定义它们的接口。

### 建议准备的样例资料

- 一份简短的主题说明，说明哪些内容是必讲重点、哪些内容不希望出现。
- 3–10 条可核查的核心来源，优先使用权威机构、出版物或可靠的一手材料；来源不足时让系统明确报告不足。
- 一份人工认可的简短事实清单，标明确定事实、争议点和不可擅自改写的历史结果。
- 一份期望输出样例，帮助判断故事大纲、分支图和场景脚本的颗粒度是否合适。

如果暂时没有人工整理的事实清单，也可以让第一轮生成它，但须由人核查后再把它作为后续剧本的事实底稿。

### 开始写代码前要形成的项目文件

- `schemas/story.schema.json`：剧情节点、选项、状态、结局、事实引用和素材占位符的格式约定。
- `schemas/source.schema.json`：来源元数据和事实陈述的格式约定。
- `workflows/topic-to-story.md`：每一步的输入、输出、失败条件和重试方式。
- `skills/`：历史研究、影游改编、分支设计、剧情编写、校验等 Skill 的独立说明。
- `examples/`：试跑主题、来源、人工审定事实清单和期望产物。

具体文件格式可以随所选 Agent 平台调整；先固定数据结构和各步骤交接内容，能降低之后迁移平台的成本。

### 可以等原型验证后再准备

- 账号、数据库、云端协作、付费和用户管理。
- 正式拍摄、视频生成、配音及完整素材库。
- 可视化剧情编辑器和复杂的多人审核系统。
- 多主题内容商城或大规模历史知识库。

因此，当前最小启动包是：**一个试跑主题 + 可核查来源 + 明确的剧本包样例 + 运行平台选择**。完成这四项后，就可以开始定义 schema、搭建 Workflow 并做第一次端到端生成。

## 11. 视频制作：HyperFrames 接入方案

**可以使用 HyperFrames，建议把它作为场景视频的合成与渲染层。** HyperFrames 将 HTML 组合按时间轴逐帧渲染为 MP4 等视频文件，适合制作地图动画、时间线、字幕、史料卡、旁白画面和章节转场。[官方介绍](https://hyperframes.app/docs/1-startup/1-introduction) [渲染说明](https://hyperframes.app/docs/3-guides/4-rendering)

需要把两个职责分开：

- **HyperFrames：** 将场景脚本、视觉素材和时间信息渲染为可复用的视频片段。
- **交互播放器：** 读取剧情 JSON，播放对应节点的视频，显示选项，保存状态并跳转到下一节点。

渲染后的 MP4 是固定时间线的视频文件；玩家作出选择和切换分支，应由 `movie_game` 的播放器完成。推荐每个可复用剧情节点独立渲染一个片段，剧情 JSON 通过 `media` 路径关联片段，播放器按节点顺序加载。需要传统线性影片时，再用 Workflow 选定一条路线或输出多个路线版本。

### 建议的视频工作流

1. **剧本 Workflow** 输出节点脚本、旁白、时长、字幕文本、事实引用和素材需求。
2. **素材 Workflow** 为每个节点准备经过来源/授权登记的地图、档案图像、环境画面、声音和字体；缺素材时使用明确占位素材。
3. **HyperFrames Workflow** 根据节点脚本生成 HTML composition，合成画面、字幕、旁白和动画，并渲染为节点视频。
4. **交互播放器 Workflow** 把节点视频接入剧情 JSON，在选择点叠加交互界面并处理状态跳转。
5. **发布检查 Workflow** 对照事实引用、素材清单、字幕、时长和所有分支，预览并渲染最终交付版本。

### 对历史题材的制作约束

- HyperFrames 负责合成和渲染，**不负责生成可信史料，也不自动解决影像版权或史实准确性**。
- 史料照片、地图和新闻片段要记录出处、日期、地点、授权状态；无法核实的画面使用示意图并明确标注。
- 不把 AI 生成的重现场景伪装成档案影像；不为真实人物配制无来源的历史对白。
- 旁白、字幕与画面关联到剧情节点和事实 ID，便于修正某项史实后重渲染受影响的节点。

### 首版建议

摩加迪沙试跑可先做 4–6 个以地图、时间线和来源卡为主的短场景，使用静态或授权素材验证“脚本 → HyperFrames 场景视频 → JSON 分支播放器”的链路。先不要求生成写实战斗画面，也不把整部影片渲染成一个不可分支的 MP4。

## 12. 素材来源：ComfyUI / Qwen Image 与 Pexels

两者可以互补，承担不同的素材角色：

| 来源 | 适合提供 | 不适合承担 |
| --- | --- | --- |
| ComfyUI + Qwen Image 2.1 | 原创插画、抽象气氛图、非写实的场景概念图；可生成和编辑静态图片 | 真实档案影像、未经核实的历史地图、视频片段 |
| Pexels | 通用环境照片和视频片段，用于城市、天空、道路、室内等气氛镜头 | 摩加迪沙之战的真实现场影像、特定年代/人物/部队的历史证据 |

### 摩加迪沙试跑的素材建议

- 核心地图用人工核实的地图数据和矢量图制作，不用图像模型凭提示词生成地理位置。
- Qwen 生成图只作为明确标注的插画或概念画，不能伪装成 1993 年现场照片；如涉及商业发布，先解决模型许可。
- Pexels 只用于不声称是真实战场画面的通用氛围镜头。现代街景不能剪成“摩加迪沙当年实况”。
- 历史照片、新闻画面和人物证词需要单独核实出处、授权与上下文；免费检索不代表已获得所有必要权利。
- 每个素材保存来源 URL、作者、许可类型、获取日期、用途标签；生成素材另保存模型版本、工作流、提示词和种子。
